# ShareGrams

Herramienta CASE colaborativa para diseño de datos mediante diagramas de clases UML. Proyecto académico de Software I.

## Estado actual

**Fases 1-4 — estables.** Editor UML (crear/mover/editar clases, atributos, relaciones y multiplicidades), persistencia con proyectos y usuarios, y colaboración en tiempo real vía WebSockets: varios usuarios conectados al mismo diagrama ven los cambios de los demás sin recargar la página, con concurrencia resuelta por bloqueo optimista (versión del diagrama) y roles de colaborador (dueño / Editor / Lector, con invitación, expulsión y cambio de rol en caliente).

**Fases 5-7 (IA: texto, voz, imagen) — implementadas, pendientes de verificación con la API real.** El editor incluye:
- un panel de chat para pedir ediciones puntuales en lenguaje natural ("Crear una clase Cliente", "Agregar un atributo correo de tipo String a Cliente"), que se traducen a los mismos `Command` que usa el editor manual — nunca genera un diagrama completo de una descripción;
- un botón de micrófono que dicta esa misma instrucción por voz (Web Speech API del navegador, sin motor de voz propio: solo llena el input de texto, el usuario revisa y manda);
- un botón "Importar imagen" que reconoce un diagrama de clases a partir de una foto o captura y arma una vista previa (clases, atributos, relaciones) para confirmar antes de aplicar nada al diagrama real.

Toda la lógica de traducción/resolución está cubierta por tests con el proveedor de IA mockeado, pero ninguna de las tres todavía se corrió contra la API real de Anthropic (falta configurar `ANTHROPIC_API_KEY`, ver más abajo).

**Fase 8 (XMI / interoperabilidad con Enterprise Architect) — implementada y verificada de punta a punta.** A diferencia de las fases de IA, esta no depende de ningún servicio externo: es conversión de formato pura, 100% en el navegador (`packages/uml-core`, sin tocar el backend). Los botones "⬇ Exportar XMI" y "📄 Importar XMI" del editor exportan/leen XMI 2.1 (UML2). El export se probó exportando un diagrama real y abriéndolo en Enterprise Architect; el import se probó contra un archivo exportado desde EA real, incluido tal cual como fixture de test (`packages/uml-core/tests/xmiImport.test.ts`). Solo soporta XMI 2.1/UML2 (el dialecto que exporta EA cuando se elige esa versión explícitamente) — no el XMI 1.1/UML 1.3 legado, que es una estructura completamente distinta.

**Fase 9 (modelo UML → modelo relacional) — implementada y testeada.** Transformador puro y determinista en `packages/uml-core/src/relational/` (`transformUmlToRelational`): sin dependencias de framework, sin tocar HTTP/React. Convierte el `UMLModel` canónico en un `RelationalModel` explícito (tablas, columnas, PK simples/compuestas, FK, constraints UNIQUE), resolviendo 1:1, 1:N y N:M a partir de las multiplicidades, y herencia (GENERALIZATION) con estrategia JOINED. Requirió un único cambio aditivo al modelo canónico: `UMLAttribute.isPrimaryKey?`. Limitaciones documentadas: no soporta todavía `Enumeration` ni `AssociationClass` (el modelo UML no los tiene), ni multiplicidades acotadas exactas (ej. `2..5`).

**Fase 10 (generador de backend Spring Boot) — implementada, testeada, y el backend generado COMPILA de verdad.** Nuevo módulo `packages/uml-core/src/generator/springboot/`, que consume exclusivamente el `RelationalModel` de la Fase 9 (nunca vuelve a interpretar el UML). Genera un proyecto Maven/Spring Boot 3.5.16 (Java 17) completo: entidades JPA, repositorios, servicios (`@Transactional`), controladores REST, DTOs planos (para evitar ciclos de serialización sin `@JsonIgnore` disperso — incluye las colecciones `@ManyToMany`, expuestas como `Set<Long>` de ids), manejo de errores (404 explícito y 409 ante violación de constraints, vía `GlobalExceptionHandler`), Bean Validation, configuración PostgreSQL por variables de entorno (puerto también configurable, `SERVER_PORT`), Swagger/OpenAPI y README. Soporta PK simple (`@GeneratedValue(IDENTITY)`), PK compuesta (`@EmbeddedId` + `@MapsId`), relaciones `@ManyToOne`/`@OneToOne`/`@ManyToMany` derivadas directamente de la metadata de la Fase 9, y herencia JOINED (`@Inheritance`/`@PrimaryKeyJoinColumn`). Limitación documentada: las tablas asociativas con atributos propios (join table con columnas extra, hoy no producible por la Fase 9) generan Entity + Repository completos, pero el Service/Controller de esos casos solo exponen listar y crear (no hay todavía una convención de URL para PK compuesta en el path).

**Fase 11 (verificación integral del backend generado) — implementada; demuestra con ejecución real que el backend generado funciona.** Nueva infraestructura de pruebas E2E en `packages/uml-core/e2e/` (`npm run test:e2e` dentro de `packages/uml-core`, separada de la suite rápida): por cada fixture, genera un backend real, lo escribe a disco, lo compila y empaqueta con Maven, crea una base PostgreSQL aislada y descartable (no hay Docker/Testcontainers en este entorno — se documentó como adaptación, usando el PostgreSQL local real de la app, nunca H2), arranca el jar en un puerto libre, espera a que responda de verdad por HTTP, ejecuta un escenario CRUD/relacional completo contra la API, y limpia todo (proceso, base, directorio temporal) pase o falle el test. 5 fixtures (CRUD+1:N+nullable+errores+JSON, 1:1 con UNIQUE real, N:M, entidad asociativa con PK compuesta, los 8 tipos de dato soportados) + 27 tests, todos verdes. Este proceso encontró y corrigió 4 bugs reales de la Fase 10 (nunca detectados por los tests unitarios, que solo comprobaban el string generado, no la ejecución real): faltaba `@Transactional` en el Service (una colección `@ManyToMany` reemplazada en una entidad *detached* no se sincronizaba con la base), faltaban los imports `JoinColumn`/`Producto` en dos casos donde otro import "de suerte" los tapaba, y el `GlobalExceptionHandler` no manejaba violaciones de constraint de base de datos (devolvía 500 en vez de 409 ante un duplicado de UNIQUE o de PK compuesta).

**Fase 12 (descubrimiento dinámico del backend) — implementada.** Objetivo: la app móvil no puede conocer de antemano qué entidades tiene un backend generado (Ventas ≠ Clínica ≠ Biblioteca). Se evaluó primero si el OpenAPI que ya genera Fase 10 alcanzaba — no: confirmado contra un backend real corriendo, `PedidoResponse.clienteId` aparece como `integer` sin ninguna marca de que es una FK, su cardinalidad, ni cuál campo es la PK. Se agregó un **Domain Manifest** versionado (`packages/uml-core/src/generator/manifest/`, `generateDomainManifest`), generado automáticamente a partir de `UMLModel` + `RelationalModel` (nunca a mano, nunca parseando el Java generado) y servido por todo backend generado en `GET /api/meta` (infraestructura de solo lectura, no una entidad — sin Repository/Service). El Manifest describe entidades, campos, tipos normalizados, PK, relaciones con cardinalidad explícita y operaciones realmente expuestas. Nueva app **`apps/mobile`** (React Native + Expo, TypeScript): pantalla de conexión (URL del backend) + pantalla de discovery (lista lo que encontró), sin CRUD ni formularios todavía (eso es Fase 13). Importa los tipos del Manifest directamente de `@sharegrams/uml-core` (sin duplicar el contrato). Prueba de aceptación real: el mismo mecanismo de descubrimiento (`GET /api/meta` + validación) descubre un backend de Ventas (Cliente, Pedido) y, sin recompilar nada, un backend de Clínica completamente distinto (Paciente, Médico, Consulta) — ambos compilados y corriendo de verdad. Limitación honesta: no hay emulador Android/navegador headless en este entorno de desarrollo, así que la confirmación visual en la UI de la app queda pendiente de una corrida manual; el mecanismo de descubrimiento en sí está probado de punta a punta contra backends reales.

**Fase 13 (motor dinámico de operaciones) — implementada.** Objetivo: que la app móvil pueda ejecutar CRUD sobre cualquier entidad descubierta por la Fase 12 sin un `Repository`/`Service` por entidad. Nuevo motor en `apps/mobile/src/engine/`: `DynamicCommand` (acciones cerradas `LIST|GET|SEARCH|CREATE|UPDATE|DELETE|COUNT`, sin propiedades ajenas como `url`/`sql`/`shell`) → `CommandValidator` (valida entidad/operación permitida/campos/required/tipos/enum/relaciones **exclusivamente contra el Domain Manifest** del backend conectado, nunca hardcodeado por nombre de entidad) → `CommandExecutor` → `DynamicRepository` (arma la URL desde `entity.endpoint`) → `DynamicApiClient` (HTTP+JSON genérico). `runDynamicCommand()` es el único punto de entrada (Validator siempre antes que Executor) — mismo punto que usará el asistente de IA en una fase futura, que **todavía no se toca acá**. Hallazgo real durante el diagnóstico: Fase 10 reusa el mismo Request DTO (mismas `@NotNull`/`@NotBlank`) en `POST` y `PUT`, así que `UPDATE` exige los mismos campos `required` que `CREATE` — no hay PATCH real, el Validator respeta ese contrato en vez de inventar semántica de actualización parcial. `SEARCH`/`COUNT` no existen como endpoints en el backend generado: resueltos como `LIST` + filtro/conteo en memoria, documentado como límite de este MVP (no escalable), encapsulado en el Repository. Las pantallas de la app ahora pasan por este motor en vez de llamar `fetch` directo; se sumó una pantalla de desarrollo (`CommandConsoleScreen`, explícitamente no es la UI final) para correr un `DynamicCommand` escrito a mano. Verificado con dos tests E2E reales (`apps/mobile/e2e/`, `npm run test:e2e` dentro de `apps/mobile`, reutiliza la infraestructura de Fase 11): Ventas (Cliente/Pedido — CRUD completo, relación opcional, y un `DELETE` bloqueado por una FK real devolviendo `CONFLICT`, no 500) y Clínica (Paciente/Médico/Consulta — mismo build sin recompilar, relaciones **requeridas** Consulta→Paciente+Medico validadas y persistidas de verdad).

**Fase 14 (interfaz móvil dinámica) — implementada.** Objetivo: una UI genérica basada en metadata (nada de `PacienteScreen`/`ConsultaForm` por dominio) que permita listar, ver el detalle, crear, editar, eliminar y manejar relaciones sobre cualquier backend descubierto, reutilizando exclusivamente el motor de Fase 13. Flujo: `DynamicHome` (`DiscoveryScreen`, ya existía) → `DynamicEntityList` (`EntityRecordsScreen`: LIST vía Fase 13, estados loading/empty/error con reintento, tarjetas tocables que solo muestran `displayField`) → `DynamicEntityDetail` (`DynamicEntityDetailScreen`, nueva: muestra todos los campos con un renderer de *display* centralizado — `src/domain/fieldDisplay.ts` — y las relaciones resueltas a su `displayField` vía `RelationValue.tsx`, con "Editar"/"Eliminar" visibles solo si el Manifest declara esa operación) → `DynamicEntityForm` (`EntityCreateScreen.tsx` renombrado a `DynamicEntityFormScreen.tsx` y extendido con un modo `edit` — mismo componente para CREATE/UPDATE, nunca dos formularios separados). `DELETE` pide confirmación nativa (`Alert.alert`) antes de ejecutar el `DynamicCommand`. Bug real encontrado y corregido en el camino: el `<Modal>` de React Native renderiza en una superficie nativa aparte, así que el `SafeAreaView` de `App.tsx` no protegía el contenido de los formularios contra la barra de estado — cada pantalla que se monta dentro de un Modal necesita su propio `SafeAreaView`. Prueba de aceptación real (mismo build, sin recompilar): backend Ventas — CREATE/LIST/detalle/UPDATE/DELETE completo de Cliente, verificado contra Postgres real en cada paso; luego, sin recompilar, backend Clínica — CREATE de Paciente y Médico, y CREATE de Consulta usando el selector de relaciones dinámico (`RelationPicker`, ya existía desde Fase 13) para elegir ambos por su `displayField`, con la relación persistida por id real (`pacienteId`/`medicoId`) en Postgres.

**Fase 15 (lenguaje natural → `DynamicCommand` mediante Claude) — implementada y verificada de punta a punta contra la API real de Anthropic.** Objetivo: escribir un pedido en lenguaje natural ("Creá un paciente llamado Carlos") y que se traduzca a un `DynamicCommand` de la Fase 13 — Claude nunca ejecuta nada directo, ni genera SQL/URLs/código, ni tiene su propia arquitectura de IA paralela: reutiliza el mismo patrón de integración de las Fases 5-7 (`AssistantService`, Anthropic SDK, `tool_choice: "any"`, API key solo en el servidor). Nuevo módulo `apps/api/src/dynamic-assistant/`, endpoint `POST /dynamic-assistant/interpret`: recibe la instrucción + el Domain Manifest del backend conectado y construye las tools de Anthropic **dinámicamente** por request (un tool por operación de `DynamicCommand` — `list_records`/`get_record`/`create_record`/`update_record`/`delete_record` —, cada uno con el parámetro `entity` restringido por `enum` del JSON Schema **solo** a las entidades que soportan esa operación puntual según el Manifest; un tool se omite entero si ninguna entidad la soporta). Nunca hay un nombre de entidad hardcodeado. Tres tools de control siempre presentes: `ask_clarification` (pedido ambiguo), `report_invalid_request` (entidad/campo inexistente — nunca inventa datos) y `report_unsupported` (fuera del schema cerrado de la Fase 13, ej. "borrar todos"). En el móvil, `apps/mobile/src/ai/aiCommandInterpreter.ts` llama a ese endpoint por HTTP (el móvil nunca tiene la API key) y `coerceAiCommand.ts` normaliza tipos de valores antes de pasar por `CommandValidator`, que sigue siendo la autoridad final — un valor que no calza se deja tal cual para que el Validator lo rechace con un diagnóstico claro, nunca se fuerza una conversión incorrecta. UI nueva mínima (`AIChatScreen`, botón "🤖 Asistente (IA)" en `DiscoveryScreen`): sin memoria conversacional, cada instrucción es un pedido stateless independiente que muestra el comando generado y el resultado real de ejecutarlo vía `runDynamicCommand`. 18 tests nuevos (13 servicio + 5 tools en `apps/api`, 9 interpreter + 8 coerce en `apps/mobile`), toda la lógica de construcción de tools/parseo de respuesta cubierta con el SDK de Anthropic mockeado. A diferencia de las Fases 5-7 (todavía nunca ejecutadas contra la API real), esta fase sí se probó de punta a punta con un `ANTHROPIC_API_KEY` real: contra un backend generado real (entidades Estudiante/Universidad/Materia) se confirmaron los cuatro caminos — CREATE exitoso ("Creá una universidad llamada UMSA en La Paz" → persistido de verdad en Postgres), `ask_clarification` cuando Claude no puede resolver un nombre a un id numérico en una sola llamada de tool (no encadena LIST+CREATE, ya que es una sola invocación de tool por instrucción), CREATE con relación una vez dado el id explícito (persistida de verdad, `universidadId` real en la fila), y `report_invalid_request` ante una entidad inexistente ("profesor"), que respondió listando únicamente las entidades reales del Manifest sin inventar nada.

**Ajuste post-verificación**: al probarlo en vivo se notó que el asistente pedía SIEMPRE el id explícito de cualquier registro referenciado por nombre ("la universidad UMSA"), incluso cuando ese registro ya existía — porque Claude solo hace una llamada de herramienta por instrucción, sin encadenar un LIST antes del CREATE. Se agregó `knownRecords` (`apps/mobile/src/ai/knownRecords.ts`): antes de llamar al intérprete, la app arma un resumen (id + `displayField`, tope de 20 por entidad) de los registros existentes de las entidades que son destino de alguna relación, y se lo manda como contexto extra al `system prompt`. Esto lo hace la app móvil y no el servidor a propósito: `apps/api` no necesariamente puede llegar a la URL del backend generado (puede ser una dirección solo válida desde el emulador, ej. `10.0.2.2`), mientras que la app móvil ya sabe hablarle. Con esto, Claude resuelve el nombre al id real en la misma llamada y solo usa `ask_clarification` si el nombre no aparece en la lista o es ambiguo — probado en vivo: "Creá un estudiante... en la universidad Gabriel Rene Moreno" resolvió `universidadId` sin preguntar nada.

**Fase 16 (interacción por voz, Speech-to-Text) — implementada y verificada en vivo contra el motor de voz real del sistema.** Objetivo: sumar la voz como un canal de entrada más, que ÚNICAMENTE convierte audio a texto — `Audio → Speech-to-Text → Texto → AICommandInterpreter (Fase 15) → Claude → DynamicCommand → CommandValidator (Fase 13) → Executor`, sin lógica de negocio propia ni una segunda arquitectura de IA paralela. Nueva abstracción en `apps/mobile/src/speech/`: `SpeechRecognitionProvider` (interfaz, para no acoplar la app a un motor de voz específico) implementada por `expoSpeechRecognitionProvider.ts` sobre el paquete `expo-speech-recognition`, que envuelve el reconocedor nativo del sistema operativo (Android `SpeechRecognizer` / iOS `SFSpeechRecognizer`) — elegido sobre una API cloud paga porque no tiene costo por uso, no necesita una key de servidor nueva, y es coherente tanto con la intención "offline-first" del roadmap original como con la decisión ya tomada en Fase 6 (web) de usar el motor nativo del navegador en vez de un proveedor externo. `SpeechToTextService` envuelve al provider en una API basada en promesas (`listen`/`cancel`), maneja permisos (pedido, denegado, denegado para siempre) y timeout, y nunca interpreta nada — solo entrega texto. `useSpeechToText` es el hook de React con los 5 estados pedidos (`IDLE`/`LISTENING`/`PROCESSING`/`SUCCESS`/`ERROR`) para la UI. `AIChatScreen` gana un botón 🎤: el texto reconocido solo llena el input (igual que en Fase 6 web, nunca se auto-envía — el usuario sigue tocando "Enviar" él mismo), con aviso si la confianza es baja. Se agregó además una confirmación explícita (`Alert`) antes de ejecutar cualquier DELETE generado por el asistente, dictado o escrito. 12 tests nuevos para `SpeechToTextService` (audio válido, error del provider, permiso rechazado con y sin poder reintentar, timeout, respuesta vacía, cancelación). Verificado con el módulo nativo REAL instalado (rebuild completo vía `expo prebuild` + `expo run:android`, no solo mocks): en el emulador se disparó el diálogo real de permiso de micrófono de Android, se concedió, el indicador nativo de "grabando audio" se activó, el motor de voz real (`es-419`) escuchó de verdad, y se probaron ambos caminos de error reales (el nativo `no-speech` y el `timeout` propio), mostrando los mensajes en español. La confirmación de DELETE también se probó (cancelar y confirmar) con un comando real generado por Claude. Full suite tras esta fase: uml-core 146/146, api 113/113, web 9/9, mobile 131/131.

**Fase 17 (offline-first + sync engine) — implementada y verificada en vivo, ciclo completo offline→sync.** Objetivo: que la app móvil funcione sin conexión — consultar, crear, editar y eliminar localmente, y sincronizar después — sin que la UI dinámica se entere si está online u offline. Nada de caché simple: `Local Database → Sync Queue → Sync Engine → Backend`. Se extrajo `DynamicDataSource` (interfaz de 7 métodos idéntica a la que ya tenía `DynamicRepository`) para que `CommandExecutor`/`runDynamicCommand` acepten cualquier implementación sin cambios de lógica. Nuevo módulo `apps/mobile/src/offline/`: `LocalDynamicEntity` (representación genérica de cualquier entidad — `localId`/`remoteId`/`values`/`syncStatus`, nunca modelos fijos por dominio), `LocalDataSource` (CRUD local con soft-delete/tombstone para lo ya sincronizado), `SyncQueue` (cola FIFO de `DynamicCommand` pendientes, reutiliza Fase 13 tal cual), `SyncEngine` (drena la cola contra el backend real, reescribe ids locales a ids remotos en relaciones cuando el "padre" ya sincronizó — con skip-y-reintento si todavía no —, detecta conflictos comparando el estado remoto actual contra la última copia conocida ya que Fase 10 no genera `@Version`/`updatedAt`, y corta toda la pasada ante un error de red en vez de reintentar a ciegas) y `OfflineFirstDataSource` (el reemplazo directo de `DynamicRepository` que usa la UI — lecturas siempre locales, escrituras locales + encoladas). Base local: `expo-sqlite`, dos tablas genéricas (`local_entities`, `sync_queue`) guardando cada registro como JSON — elegido sobre WatermelonDB/Realm precisamente porque esos exigen modelos por entidad, lo que iba contra el requisito central de esta fase. Conectividad real vía `@react-native-community/netinfo` (no existía ninguna detección antes) dispara sync automático al recuperar conexión; botón manual "Sincronizar ahora" y badge "☁ Pendiente de sincronizar" en listas/detalle cuando el id todavía es local. Toda la lógica (`LocalDataSource`/`SyncQueue`/`SyncEngine`/`OfflineFirstDataSource`) se testea con un `InMemoryRecordStore` en memoria — 72 tests nuevos — sin tocar SQLite real; solo el adaptador `SqliteRecordStore` queda sin test unitario (verificado en vivo, mismo criterio que el módulo de voz de Fase 16). Dos bugs reales encontrados en vivo: React Native (Hermes) no tiene un `crypto` global como el navegador (`expo-crypto` como reemplazo, inyectado por constructor para no envenenar los tests con un módulo nativo no parseable), y faltaba una hidratación inicial (`SyncEngine.hydrate()`) para que los registros ya existentes en el servidor aparecieran la primera vez que te conectás. Prueba de aceptación real en el emulador: conectar → aparecen los registros ya existentes (hidratación) → WiFi apagado → crear un registro nuevo → badge "Pendiente de sincronizar" → WiFi reactivado → sync automático sin tocar nada → "✅ 1 sincronizado" → confirmado en Postgres real con su id definitivo → el badge desaparece.

## Estructura del repositorio

```
packages/
  uml-core/    # Modelo UML canónico, catálogo de comandos y CommandHandler (sin dependencias de framework)
apps/
  api/         # Backend NestJS + Prisma: auth, proyectos, diagramas, colaboración en tiempo real y asistente de IA
  web/         # Editor UML (React + Vite + React Flow + Zustand)
  mobile/      # Descubrimiento (Fase 12) + motor de operaciones (Fase 13) + UI dinámica CRUD (Fase 14) + asistente en lenguaje natural (Fase 15) + dictado por voz (Fase 16) + offline-first/sync (Fase 17) contra el backend generado (React Native + Expo)
```

Regla de arquitectura: el canvas nunca modifica el modelo directamente. Toda mutación pasa por un `Command` (CREATE_CLASS, MOVE_CLASS, ADD_ATTRIBUTE, CREATE_RELATIONSHIP, UPDATE_MULTIPLICITY, etc.) que `uml-core` valida y aplica. Esta es la misma vía que usan el editor manual, la colaboración en tiempo real, el asistente de IA y el importador de imagen/XMI (que arman un batch de comandos y lo aplican con el mismo dispatch, tras una vista previa), y la que va a reutilizar el generador de Spring Boot en fases posteriores.

## Cómo correr el proyecto

Requisitos: Node.js 20+, PostgreSQL.

```bash
npm install              # instala todas las dependencias del monorepo (workspaces)
```

**Backend** (`apps/api`): copiar `apps/api/.env.example` a `apps/api/.env` y completar `DATABASE_URL` y `JWT_SECRET`. `ANTHROPIC_API_KEY` es opcional: sin ella, el resto de la API funciona normal y el asistente de IA responde que no está configurado.

```bash
npm run prisma:migrate   # aplica las migraciones a la base
npm run dev:api          # levanta el backend en http://localhost:3000
```

**Frontend** (`apps/web`):

```bash
npm run dev:web           # levanta el editor en http://localhost:5173
```

**Tests:**

```bash
npm run test:uml-core   # tests del modelo UML, export/import XMI
npm run test:api        # tests del backend (auth, proyectos, diagramas, tiempo real, asistente de IA, reconocimiento de imagen)
npm run test:web        # tests del store del editor
npm test                # corre los tres
```

## Comandos UML soportados (Fase 1-2)

`CREATE_CLASS`, `UPDATE_CLASS`, `MOVE_CLASS`, `DELETE_CLASS`, `ADD_ATTRIBUTE`, `UPDATE_ATTRIBUTE`, `DELETE_ATTRIBUTE`, `CREATE_RELATIONSHIP`, `UPDATE_RELATIONSHIP`, `DELETE_RELATIONSHIP`, `UPDATE_MULTIPLICITY`.

Tipos de relación soportados: `ASSOCIATION`, `AGGREGATION`, `COMPOSITION`, `GENERALIZATION` (esta última sin multiplicidad). El tipo de una relación es inmutable tras crearla: para cambiarlo, se elimina y se vuelve a crear.
